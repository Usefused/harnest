# Packs and branded CLIs: how they work inside

A Harnest pack is how a company gives its teams their own command (for example
`acme`), its own defaults for new agents, migrations for existing agents, and
optionally a customized Studio. Using packs is covered in the public
[Company project packs](https://usefused.com/docs/harnest/build/project-packs)
docs. This page covers how they are built and where to change them. The decisions behind the design are in
[../development.md](../development.md#pack-implementation-contract).

## What a pack is

A pack is one folder:

- `pack.yaml`: inert data, read without running code. It holds `name`,
  `version`, `title`, `description`, `command` (the branded command name),
  `requires` (Harnest and Studio versions), and an optional `studio:` sub-pack.
- `pack.py`: optional and trusted. It defines
  `pack = ProjectPack(schema_version=..., options=..., templates=...)` with
  `@pack.initialize` (new agents), `@pack.migration(from_version=,
  to_version=)` (existing agents), and `@pack.command(name)` (company
  subcommands).

Hooks never write files directly. They return a `ChangePlan` built from
`context.files` (`write_text`, `from_template`, `from_file`, `delete`) and
`context.yaml` (`set`, `rename_key`). Harnest shows the combined plan, then
applies it in one transaction. `examples/packs/acme` uses every feature.

## How one command flows

`acme init my-agent --option team=payments`:

1. **Branded launcher.** `acme` is the console script from the
   `harnest-pack-acme` wheel. Its launcher, generated by
   [authoring/distribution.py](../../src/harnest/authoring/distribution.py),
   uses only the standard library. It turns `init`, `upgrade`, and `studio`
   into `harnest <same command> --pack <installed pack folder>`. It turns the
   pack's own commands into `harnest pack run`, and passes anything else to
   `harnest` unchanged. It runs whatever `HARNEST_CLI` names, or `harnest` on
   `PATH`.
2. **Go CLI.** [init.go](../../cmd/harnest/init.go) `runPackInit` (or
   `runPackUpgrade` in [upgrade.go](../../cmd/harnest/upgrade.go)) resolves the
   pack folders and runs `python -m harnest.cli pack init ...`
   ([pack_commands.go](../../cmd/harnest/pack_commands.go)).
3. **Load.** [authoring/pack_cli.py](../../src/harnest/authoring/pack_cli.py)
   calls [authoring/packs.py](../../src/harnest/authoring/packs.py). That
   parses `pack.yaml` (`read_manifest` is the only parser), checks `requires`,
   imports `pack.py`, and validates `--option` values against the pack's
   options model.
4. **Plan.** [authoring/planner.py](../../src/harnest/authoring/planner.py)
   `ProjectPlanner` first runs core `harnest init` (or core upgrade) into a
   staging folder. It then runs each pack's hooks against that staged tree.
5. **Apply operations.**
   [authoring/operations.py](../../src/harnest/authoring/operations.py)
   `OperationEngine` applies each operation and records who owns what in the
   agent's `harnest-packs.lock` (pack schema versions, `claims` with content
   digests, and Studio install `resources`).
6. **Publish.** [authoring/filesystem.py](../../src/harnest/authoring/filesystem.py)
   checks destination digests, backs up changed files, and applies the staged
   plan. Handled failures restore the backup; interrupted transactions require
   recovery. `pack_cli.py` owns plan display.

Ownership is the core safety rule. A pack may replace a file or YAML key only
if it created it and nobody has edited it since (the digest still matches).
`WritePolicy.IF_MISSING` (the default) skips anything that already exists.
`WritePolicy.MANAGED` updates content the pack owns. Anything else is reported
for review instead of overwritten. This keeps a migration from clobbering a
team's edits.

Studio reads only the `studio:` section, using
[studio/src/harnest_builder/pack_manifest.py](../../studio/src/harnest_builder/pack_manifest.py)
and `packs.py`. It never imports `pack.py`.

## Building and distributing a branded CLI

The public [Build a company CLI](https://usefused.com/docs/harnest/build/project-packs/cli)
page covers `harnest pack init|validate|build` and publishing. Two internal
points matter when you change it: the wheel holds only the pack folder and the
launcher, with no dependencies (so it never vendors Python, Harnest, Studio,
or credentials), and the launcher finds Harnest through `HARNEST_CLI` or
`PATH` at run time.

## Dependency ownership

Core initialization owns `pyproject.toml`. Pack operations can create files,
edit YAML keys, or update files already owned by the pack; they cannot modify
core-owned dependency declarations. Agent templates supply initial dependency
metadata before pack initialization runs. See the public
[agent template guide](https://usefused.com/docs/harnest/build/project-packs/cli#initialize-from-a-template)
for template selection.

## Changing the pack system itself

| To change | Edit | Test in |
| --- | --- | --- |
| `pack.yaml` fields | `PackManifest` in `authoring/packs.py`, plus the Studio sub-pack contract in `studio/src/harnest_builder/pack_manifest.py` if the field is under `studio:` | `test_project_packs.py`, `test_project_pack_studio.py` |
| A new hook or `ProjectPack` option | `ProjectPack` in `authoring/contracts.py`; call it from `ProjectPlanner` in `authoring/planner.py` | `test_project_pack_contracts.py` |
| A new operation (for example TOML keys) | A builder on `ProjectFiles`/`ProjectYAML` (or a new view) in `authoring/context.py`, and its handler in `OperationEngine` in `authoring/operations.py`. It must record and verify ownership claims like `_write` and `_yaml_set` do | `test_project_pack_contracts.py`, `test_project_packs.py` |
| What the branded launcher forwards | The launcher template in `authoring/distribution.py` | `test_project_pack_studio.py`, `test_agent_builder_packs.py` (wheel round trips) |
| Go-side commands and flags | `pack_commands.go`, `project_pack_init.go`, `init.go`, `upgrade.go`, `studio_launcher.go` | `cmd/harnest/*_test.go` |

The public authoring API is `harnest.authoring` and is part of
`tests/fixtures/public-api.json`. Any change there also needs the public pack
docs in the Mintlify repository updated.
